# 需求申请 · 本机全量历史导入（取消 90 天窗口限制）

- 编号：REQ-2026-10-14-01
- 状态：**待评审，未实现**
- 提出背景：真实数据验收中，使用者反馈“某联系人在微信里明明有去年和上个月的记录，但历史补录没补上，而且只补到不到 200 条，远没到 5,000 条上限”。
- 适用范围：只影响历史补录的**时间范围**；不改变只读边界、授权范围、发送策略与任何 AI 行为。

## 1. 现状与已验证事实

| 事实 | 证据 |
| --- | --- |
| 补录窗口固定为最近 90 天 | `HistoryJobEndpointsV1.cs:30` 不传时间即 `from = to − 90 天`；`HistoryJobEndpointsV1.cs:31` 对 `to − from > 90 天` 直接拒绝并返回 `INVALID_HISTORY_RANGE` |
| 读取器独立再校验一次同样的 90 天 | `reader.py:524` 对排队任务再次拒绝 `> 90 天` |
| 前端从不传时间范围 | `wwwroot/v8/drawers.js` 的补录动作只发 `{accountId, conversationId, maximumRows: 5000}` |
| 5,000 是**单任务行数上限**，不是目标量 | 王继森会话在 90 天窗口内本机只有 182 条文本，任务 `Completed / read=182 / failed=0 / is_last_batch=true` |
| 时间谓词对更早数据是正确的 | 只读探针（限定已授权会话）：微信本地库该会话共 109 条文本，跨度 2025-11-03 → 2026-10-13；按 `2025-10-15 → 2026-01-12` 窗口查询返回 **19 条**，按最近 90 天查询返回 70 条 |
| “无窗口”路径已经能拿到全量 | 首次安装的初始导入（`reader.py history` 不带 `--from-utc/--to-utc`）没有窗口限制，该会话因此已含 2025-11 的记录 |
| 更早时段确实可能本机无数据 | 对王继森另发 4 个显式历史窗口（2025-08、2025-05、2025-01、2024-06 各约 90 天）全部 `Completed / read=0`，即**这台电脑**的本地库里那些时段没有该会话的文本消息 |

结论：使用者看到的“补录不到去年”由策略限制造成，而非查询缺陷；但“本机到底有没有更早的记录”目前界面完全不表达，只能靠猜。

## 2. 需求描述

对**单个已授权会话**，一次操作即可把本机微信库里可读到的**全部历史文本**导入本应用，不受 90 天限制，并且让使用者清楚知道导入了什么范围、还剩下什么。

### 必须满足

1. 不再要求使用者理解“90 天”这个内部约束；入口语义为“导入本机全部可读历史”。
2. 完成后必须显示：**总条数、最早与最晚消息日期、扫描的分片/表数量、被忽略的非文本条数、失败条数**，以及“本机已无更早记录”的明确终止信号。
3. 中途可取消；已导入部分保留且幂等（重跑不产生重复）。
4. 单个时间片内消息数超过行上限时**继续翻页**，而不是整体失败。
5. 全程只读微信；不新增采集会话范围；日志与回执不落消息正文。

### 明确不做

- 不引入微信自动发送，不扩大授权会话范围。
- 不处理非文本消息（图片/语音/视频/文件）正文、附件与群聊。
- 不做跨设备/云端历史拉取（本机读不到就是读不到）。

## 3. 建议方案

### 方案 A（推荐）：服务端按 90 天滚动分片 + 片内游标翻页

保留 API 与读取器现有的 90 天/5,000 行约束不变，在其上加一层编排：

- 新增“全量回溯”任务类型或 `mode: full` 标志，服务端从当前时间向前按 ≤90 天分片连续创建子任务；
- 每个子任务内部按 `(create_time, sort_seq, local_id)` 游标翻页，避免第 4 条失败模式；
- 直到某个分片返回 0 条且已越过本机最早记录时终止，记录 `earliest_scanned_utc`；
- 进度对使用者呈现为“已回溯至 YYYY-MM · 已导入 N 条”，而不是任务数。

优点：不动两处安全/资源上限，改动集中在编排与翻页；失败可按分片重试。
代价：需要新增子任务与父任务的关联字段（一次迁移）。

### 方案 B：直接放宽 90 天上限

去掉两处窗口校验，单次任务覆盖任意跨度。
缺点：单次扫描内存与耗时不可控，5,000 行上限会立刻变成常态失败点，且两处校验要同步改，风险高于收益。**不建议**单独采用。

### 方案 C：不改产品，只改文案

把“最近 90 天”改成“本机最近 90 天，更早记录需多次回溯”，并显示最早已导入日期。
这是**任何方案都应包含**的最小改进，但不满足第 1 条需求。

## 4. 必须先修的既有缺陷

`reader.py:1244-1251`：每个分片查询用 `LIMIT max_rows + 1`，一旦该窗口内行数超过 `max_rows` 就抛 `HISTORY_ROW_LIMIT_EXCEEDED` 并终止，**没有游标翻页**。这意味着即使是 90 天窗口，消息量大于 5,000 条的会话现在也无法补录。方案 A 依赖此缺陷被修复。

## 5. 影响面

- 后端：`Modules/Conversations/Api/HistoryJobEndpointsV1.cs`（任务模型、父子任务、终止条件）、补录统计响应（已导入最早/最晚日期、忽略条数）。
- 读取器：`src/WeChatAiCopilot.Reader/reader.py`（游标翻页、跨片续扫、回执字段）。
- 数据库：一次迁移（子任务关联、`earliest_scanned_utc` 等），只在隔离库验证后再上正式库。
- 前端与 **Demo**：V8 的「历史补录」页当前写着“最近 90 天 · 最大 5,000 条”，语义必须改变 → **按门禁先改 Demo 并经批准，再改正式代码**。
- 隐私与容量：导入数年历史会显著增大本机库，并扩大 AI 上下文与记忆的可及范围。需要显式操作、明确范围显示，以及“只影响该联系人”的说明。

## 6. 验收标准（可测）

1. 对一个只有近期消息的会话执行全量导入：结果与现在一致，且明确显示“本机已无更早记录”。
2. 对存在跨年度消息的会话执行全量导入：最早记录日期与微信本地库实际最早日期一致（允许 ±1 天，因微信按本地时区归档）。
3. 构造单窗口 > 5,000 条文本的会话：导入成功、无 `HISTORY_ROW_LIMIT_EXCEEDED`、总数与本地库一致、重跑不产生重复。
4. 中途取消后重跑：从已导入位置继续，最终结果与不取消一致。
5. 全程不出现消息正文进入应用日志、Reader 回执或诊断输出（以现有脱敏断言测试校验）。
6. 未授权会话无法通过任何新参数被导入（越权仍按现有 403/404 语义拒绝）。

## 7. 需要评审决定的点

1. 采用方案 A 还是先做方案 C（仅文案与范围显示）。
2. 全量导入的默认粒度：按会话逐个触发，还是允许“对所有已监听会话一次性全量”。
3. 是否需要容量上限与提示（例如预计导入条数、磁盘占用）。
4. 导入数年历史后，AI 上下文与记忆沉淀是否需要额外的时间范围约束（当前深度档位只控制“近期消息条数”，不控制记忆时间跨度）。
