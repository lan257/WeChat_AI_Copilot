# M6 基础设施与系统管理：详细设计

> 状态：待评审；横向支撑模块，**从并行开发的第 0 阶段开始**提供最小运行/鉴权/迁移规范。  
> 原则：个人自用系统也要保护私人聊天，但不为此引入微服务集群、复杂权限平台或专职运维产品。

## 1. 目标与职责

M6 为 Windows 本地采集、ASP.NET Core 模块化单体、PostgreSQL、Web 和隔离的 Agent Runtime 提供：运行配置、单用户认证、各类专用凭据、日志脱敏、数据库迁移协调、基础任务/状态跟踪、部署和基本备份恢复说明。

M6 **不拥有**消息去重、方向交换、记忆内容、Agent 推理、前端模式逻辑。各模块可以依赖 M6 公共能力，但不得让 M6 演变为所有业务逻辑的汇聚服务。

## 2. 首版部署拓扑

```text
Windows 本机（微信客户端正常运行）
  ├─ M1 Reader Worker（只读、最小权限）
  ├─ ASP.NET Core（M1 接入薄层 + M2 + M3 + M4 + M6）
  ├─ PostgreSQL（一个物理实例，按模块区分数据所有权）
  ├─ M5 Web 静态资源 / 前后端网关
  └─ [可选] 隔离 Agent Worker / Codex CLI
           ↑ 经认证的浏览器访问（局域网或之后的远程接入）
       手机微信分屏 / 桌面浏览器
```

首版允许本机同机部署以复用已验证 POC。后续如远程后端化，Windows 读取器仍必须在可访问微信本地数据的主机运行；通过安全受控的上报通道连接后端。**不把远程访问可用性写成 POC 已验证事实。**

## 3. 配置分层及配置所有权

| 配置域 | 典型项 | 所有权/约束 |
|---|---|---|
| `Reader` | 允许账号/会话、读取器包版本、API 地址、允许数据类型 | M1 提交，M6 托管密钥/环境覆盖 |
| `Database` | PostgreSQL DSN、迁移编号、连接池 | M6，禁止外泄给浏览器与 Agent |
| `WebAuth` | 单用户身份、会话时限、Cookie/Token/CSRF 策略 | M6 |
| `Agent` | Runtime 选择、模型 API 凭据、执行时限、预算、并发 | M4 消费，M6 安全管理 |
| `History` | 最大扫描范围、每批上限、允许任务并发、超时 | M1/M2 决定语义，M6 存配置 |
| `Observability` | 日志级别、审计保留、脱敏、健康检查 | M6 |

本地开发 `.env` 可用于启动，但真实 Token/密钥不得写入源码库、调研报告、调试截图或 Agent 输入。前端设置页不得提供可读取完整数据库连接串的接口。

## 4. 身份认证与授权模型

首版是个人自用，不需要租户系统。至少区分两种调用主体：

- **Web 用户会话**：经登录授权后读取其允许账号/会话，修改记忆、选择目标微信账号视角、发起历史补录和 AI 咨询。
- **本机 Reader 身份**：独立认证，只允许上报其绑定的账号/会话、报告状态及领取被授权的补录任务。不能使用 Web cookie 作为机器长期凭据。

原则：所有 M2/M3/M4 账号/会话授权由后端核验，不因个人自用而省略。修改操作要求 CSRF 防护、合适的 SameSite/Cookie 策略或其它等效受控机制。跨域访问默认收紧到预先允许的来源，不向任意 Origin 暴露带凭据私聊接口。

**必禁接口：** 微信代发消息、任意 SQL 查询、读取微信密钥/明文数据、Agent 运行任意主机 Shell、全库导出未鉴权下载。

## 5. 数据保护与隐私

- PostgreSQL 与备份包含敏感聊天原文。限定账号权限、数据库绑定地址、访问控制和必要的磁盘保护；不把数据库未鉴权暴露到公网。
- 本机读取器可能生成临时明文 DB，文件仅限必要目录和最短保留，任务成功/失败/异常退出要有清理与核查方案；不得让 Web 直接下载原始数据库。
- 日志只输出 `runId/jobId/correlationId`、错误码、计数、时间、匿名化会话定位，不包含正文、源 sender ID、微信凭据、模型完整 Prompt/工具上下文。
- 日志脱敏覆盖 ASP.NET Core middleware、Reader stderr/stdout、M4 CLI/模型返回错误和异常堆栈；统一防止异常对象把私聊内容带入日志。
- 第三方模型调用前，M4/M3 选择**当前会话必要片段**，不能默认上传所有联系人多年聊天；模型服务商的隐私/留存条件应当在实际部署中明确。
- 用户主动删除/更正数据与历史补录“只补不删”是不同流程；首版至少可删除用户在 M3 中创建的人工记忆，原始聊天彻底删除的流程列为单独功能决策，不可被历史同步意外覆盖。

## 6. 数据库迁移与模块表所有权

一套 PostgreSQL 物理实例；单个迁移执行入口，避免四个开发 Agent 同时运行相互冲突的 DDL。职责建议：

| 数据域 | DDL/实体负责人 | M6 负责 |
|---|---|---|
| `chat_accounts / contacts / conversations / chat_messages / message_sources / sender_calibrations` | M2 | 迁移顺序、统一命名规范、环境执行 |
| `memory_items / memory_evidence` | M3 | 迁移登记与授权 |
| `agent_runs / suggestion_batches / agent_threads / agent_turns` | M4 | 迁移登记与脱敏 |
| `capture_state / history_jobs` | 由 M1/M2 共同确定唯一写入者 | 任务状态基础表/运行配置协调 |

**迁移顺序：** 公共基础 → M2 核心表 → M1 补录任务所需表（若独立） → M3 记忆表 → M4 任务表。各模块负责人提交 SQL/迁移脚本供单一集成负责人审查；避免并行分支互相修改同一迁移文件。已有 POC 库需迁移验证及回滚计划，不能直接丢弃重建真实数据。

## 7. 系统状态与健康检查

| 状态 | 含义/来源 | 用户视图建议 |
|---|---|---|
| `ApiReady` | ASP.NET Core 服务响应 | “API 可用” |
| `DatabaseReady` | PostgreSQL 读写/迁移状态 | “消息存储可用” |
| `ReaderConnected` | Reader 通道在线 | “读取器在线” |
| `CaptureActive` | 指定目标在实际采集 | “正在监听当前配置目标” |
| `CaptureGapPossible` | 读取器曾异常/可能有空窗 | “可能存在消息缺口，可补录” |
| `HistoryJobRunning/Partial` | 受限补录任务状态 | “本次扫描进度 / 未确定项” |
| `AgentReady/Running/Failed` | Agent 可接受/执行任务 | “AI 生成中 / 失败” |

**不得混用“进程在线”和“消息完整”**。基础版可以用简单 REST 健康检查和后台任务表；不上 Prometheus/复杂消息总线作为前置条件。健康响应公开给浏览器时不能包含连接串、内部路径和账户原始 ID。

## 8. 任务管理、恢复与退出

- M1 历史补录长任务使用 `jobId`，状态从 `Pending` 到 `Running` 再到终态；可观测输入范围、read/matched/created/needsReview 等计数，支持用户取消和重复尝试。取消不删除已入库的合法历史。
- M4 Agent 运行有 `runId`，状态/时限/取消和错误；Agent 异常不能阻塞 Reader 或消息入库。
- 对持久化成功后的通知失败，Web 通过 M2 游标补拉实现最终可见性；实时通知不被当成唯一来源。
- 应用退出时控制 Worker 和本机临时文件生命周期；重启后能够区分“等待重试的任务”和“无法保证已读完整的时间段”。
- 后台任务可先在 ASP.NET Core 内执行受控 Worker，之后才评估独立队列；不要求拆微服务。

## 9. 统一错误模型与观测

对所有 API 使用 `error.code / message / retryable / correlationId`；区分：用户输入错误、权限错误、ID/校准版本冲突、微信读取器不可用、历史源范围部分缺失、模型失败/预算耗尽、数据库不可用。

基本审计应覆盖：Web 登录、采集目标修改、目标微信账号视角选择、历史补录启动/取消、人工记忆修改、Agent 任务类型与最终状态。审计日志不含聊天正文。隐私删除动作若落地，必须有独立审计和明确保留策略。

## 10. 并行开发与交付要求

1. **M6-A（第 0 阶段）**：可运行的 ASP.NET Core + PostgreSQL + Web 基础骨架、环境配置和迁移执行方法；只做必要公共设施。
2. **M6-B（第 0 阶段）**：用户身份与 Reader 机器身份的最小安全边界、OpenAPI/错误模型、脱敏日志规范；同步供 M1/M2/M4/M5 使用。
3. **M6-C（并行）**：Reader/Agent 运行状态聚合、健康接口、任务状态通用观测；不夺取业务任务所有权。
4. **M6-D（集成阶段）**：协调各模块迁移，启动依赖、局域网访问鉴权、机密保护、最小备份与恢复指引。
5. **M6-E（上线前）**：安全与隐私回归，特别检查手机访问权限、Codex CLI 运行权限、日志中的聊天泄露。

## 11. 验收矩阵

| 编号 | 测试 | 通过条件 |
|---|---|---|
| M6-T01 | 匿名用户访问消息/记忆/AI API | 401/403，不泄露内容 |
| M6-T02 | Reader 使用 Web 身份或 Web 使用 Reader 身份 | 权限拒绝、互不冒用 |
| M6-T03 | 已认证账号 A 查询账号 B | 资源不可见 |
| M6-T04 | Reader/Agent 异常输出包含敏感测试字符串 | 日志不保留该字符串 |
| M6-T05 | 临时明文数据库生成/异常退出 | 权限限制有效，能发现/清理残留 |
| M6-T06 | Agent 不可用但 M1/M2 工作 | 消息仍正常入库与查询 |
| M6-T07 | Web 实时连接中断恢复 | 按 M2 cursor 正确补拉 |
| M6-T08 | 重放已成功的历史补录 | 业务幂等由 M2 保证，运行状态不伪造成功 |
| M6-T09 | 升级迁移前后 | 已有 POC 数据保留，执行过程和回滚指引明确 |
| M6-T10 | 系统配置/状态接口 | 不暴露数据库密码、微信凭据、主机私有路径 |

**完成定义：** 开发和个人受控部署环境可启动、可认证、可追踪关键失败、可执行模块迁移，且 Agent/Reader 没有越权入口。生产级高可用、跨地区部署、复杂告警不进入第一期。
