# 决策记录 · 可恢复的历史扫描与本机全量导入（ADR-2026-10-14-02）

- 状态：**已采纳，实现中**
- 依据：`docs/product/proposals/2026-10-14_full-local-history-import.md`（REQ-2026-10-14-01）与
  `临时文件/WeChat_AI_Copilot_V8_Code_Optimization_Review_2026-10-14.md` §1.1、§2、§5。
- 不在范围：微信云端历史、群聊与公众号、非文本正文与附件、任何自动发送。

## 1. 要解决什么

1. **窗口是策略而不是能力**：补录固定最近 90 天（`HistoryJobEndpointsV1.cs:30-31`、`reader.py:531` 各校验一次），
   本机库里更早的文本读不到，使用者只能靠猜。
2. **扫描不可恢复**：一次扫描要么跑完要么整体失败。评审 §2 指出没有可恢复游标；读取器改成 keyset 分页之后
   仍然如此——进程或电脑中途退出，下次必须从头再扫。

两者必须一起做：只放开窗口会让“扫到一半断掉”的代价变大，只做游标又仍被 90 天挡住。

## 2. 设计

### 2.1 游标存在哪里

游标语义 = “**已成功入库**的源行位置”，不是“已读到”。因此由服务端在**接受批次的事务里**写入，
读取器崩溃不会让游标越过未持久化的数据。

新增 `023_history_scan_checkpoints`：

| 列 | 作用 |
| --- | --- |
| `account_id, conversation_id` | 授权范围，外键到 `conversations`，会话删除级联清理 |
| `window_key` | `full`（全窗口）或 `from~to`，保证续扫只用在同一请求范围上 |
| `message_table` | 微信本地分片表名，keyset 分页在表内单调 |
| `last_local_id` | 该表已入库的最大 `local_id`，下次从它之后继续 |
| `scanned_rows` | 已扫描行数，仅用于展示进度 |
| `last_job_id` | 最近一次写入该游标的任务，指向可追溯的运行记录 |

`history_jobs.maximum_rows` 的检查约束从 `1..5000` 放宽到 `1..200000`（同一次迁移），
否则全量任务在数据库层就会被拒。

### 2.2 全量任务如何表示

`requested_from_utc` 与 `requested_to_utc` **同时为 NULL** 即“本机全部可读历史”。不新增枚举列，
不改变已有 ranged 任务的语义，也不悄悄把“不传时间”的默认值从 90 天改成全量——那会让旧界面行为突变。
新界面显式提交 `fullLocalHistory=true`。

### 2.3 续扫数据流

1. `GET /api/reader/history-jobs/next` 的响应增加 `resumeCursors: [{messageTable, lastLocalId}]`，
   取自该任务 `window_key` 下的游标行。
2. 读取器 `_read_history` 每张表从 `last_local_id` 之后开始，其余分页逻辑不变。
3. 每个被接受的批次在摄取事务内 upsert 游标：`last_local_id = greatest(现值, 本批该表最大 local_id)`，
   `scanned_rows` 累加。
4. 被忽略/失败的行不会把游标推过它——回读时由既有 source 去重消化，最坏是重复扫描一小段。

### 2.4 时限与租约

`60 分钟`总执行时限（`63f2a4c`）只适用于有界窗口任务；全量任务按 `8 小时`。
无进度租约仍是 10 分钟：游标每批都刷新 `updated_at`，卡住的进程依旧会被判失败，而失败的任务
带着游标留在库里，下一次任务自然续扫。

### 2.5 界面

「联系人与会话 → 历史补录」增加一个动作「导入本机全部历史」，并显示“已从上次中断处继续 · 已扫描 N 条”；
不改动 V8 原型的既有布局结构，只在补录页现有动作区与统计区里增加内容。

## 3. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 一次性写入上万条本机消息，磁盘与时间开销陡增 | 任务仍是单会话、逐批 100 条、可取消；界面明示范围与进度 |
| 游标把中断前的旧范围错接到新范围 | 游标按 `window_key` 分键，范围不同不共享 |
| 表名来自读取器，可能被拼成恶意 SQL | 游标只做参数化写入；`message_table` 进入 SQL 前沿用既有标识符校验 |
| 迁移改动正式库 | 升级前由启动器自动完整备份并做恢复演练（`c356e30`），演练失败即中止启动；迁移先在隔离 55439 库验证 |
| 隐私外泄 | 游标只含整数位置与表名，不含消息正文、发送者或时间；不新增任何出网路径 |

## 4. 回滚

`023` 是加法：`DROP TABLE copilot.history_scan_checkpoints;` 并把 `maximum_rows` 的检查约束改回 `1..5000`
即可完全退回；已导入的消息不受影响。迁移校验和记录在 `copilot.schema_migrations`，不会静默重放。

## 5. 验收

1. 隔离库：创建全量任务 → 送两批后让任务“断电”（进程退出）→ 新任务从游标续扫，不重复导入已入库行。
2. 有界窗口任务的 90 天与 5,000 条校验仍然生效（回归不变）。
3. 真实会话：对已授权联系人执行一次全量导入，比对读取器报告的本机文本行数与应用内行数一致。
4. 界面显示续扫进度与最终覆盖状态。
